# Errata

Two issues affect the numbers reported in our Interspeech 2025 paper
([arXiv:2505.19663](https://arxiv.org/abs/2505.19663v2), Tables 4 and 5). 
One is a bug (related to DAC) in this repository that has now been fixed; the other (related to MP3) is a difference between the code used for the paper and the code released here, where the released behavior is the correct one.
Full details, including the corrected Tables 4 and 5 and the revised claims, are in the erratum appendix of [arXiv:2505.19663v3](https://arxiv.org/abs/2505.19663v3).

Corrected values below are means over 3 evaluation seeds, the same protocol as the paper.
They are reported in the paper's own notation: `✓` means ≥ 0.99, other values are truncated
to two decimals.

---

## 1. DAC attack was applied without resampling (fixed in this repository)

**What was wrong.** `DACWrapper` was constructed without a `model_sr` argument, so it fell
back to its default of `44100`. The guard meant to catch a rate mismatch,

```python
assert self.model_sr == self.codec_sr
```

therefore compared that default against the 44.1 kHz codec rate and could never fire.

Audio was handed to the DAC model at whatever rate the watermarking model used (typically 16k),
with no resampling. While `EncodecWrapper` had always resampled correctly; DAC had not.

For a 16 kHz model this means DAC processed the signal as if it were 44.1 kHz — a 2.76x
time-scale mismatch, an effective hop of 32 ms instead of 11.6 ms, and content far outside
the codec's training distribution. The attack was therefore much more destructive than a
rate-matched DAC pass.

**Which model was affected.** Every model that does not run at 44.1 kHz: AudioSeal and WavMark
(16 kHz), Timbre (22.05 kHz), and SilentCipher in its 16 kHz configuration (the one used in
the paper).

**The fix.** `DACWrapper` now takes `model_sr` from the attack pipeline, and
`reconstruct_target_n_codebook()` resamples to the codec rate and back, mirroring
`EncodecWrapper`. 
Alternatively, for the 16 kHz models (AudioSeal, SilentCipher, WavMark), setting
`attack.dac.type=16khz` now also works, in which case no resampling happens. The corrected
numbers below use the 44.1 kHz DAC with resampling, as defined in the paper.

**Corrected numbers (DA column).** Bitwise accuracy on the left, full-message accuracy on
the right. `*` marks the models retrained with strict attacks; those were retrained with
the fix applied before being re-evaluated, following the paper's own setup — AudioSeal
fine-tuned from the released weights, SilentCipher from scratch.

| Model | Eval | Bitwise (paper -> corrected) | Full-message (paper -> corrected) |
|---|---|---|---|
| AS | S | .52 -> **.96** | .00 -> **.64** |
| AS | L | .53 -> **.97** | .00 -> **.75** |
| SC | S | .32 -> .35 | .00 -> .00 |
| SC | L | .32 -> .36 | .00 -> .00 |
| TI | S | .60 -> **.69** | .00 -> .00 |
| TI | L | .62 -> **.71** | .00 -> .00 |
| WM | S | .00 -> .00 | .00 -> .00 |
| WM | L | .00 -> .00 | .00 -> .00 |
| AS* | S | .60 -> **.98** | .00 -> **.86** |
| AS* | L | .61 -> **✓** | .00 -> **.94** |
| SC* | S | .42 -> **.71** | .00 -> **.12** |
| SC* | L | .44 -> **.76** | .00 -> **.17** |

Because AS* and SC* were retrained, all of their values come from the new models, not only
DA and MP. Outside DA and MP they change by at most .04 (see the appendix linked above).

**Effect on the paper's conclusions.** WavMark's numbers do not change (it fails under DAC
either way) and SilentCipher barely moves. 
Howver, AudioSeal changes substantially: under the corrected attack it is roughly as robust to DAC as it is to EnCodec,
and after retraining it is robust to DAC. 
The following statements in the paper need revising:

- "DA has a more severe effect on all models" — DA and EnCodec now have comparable
  effects on all models (bitwise: AS .96 vs .96, SC .35 vs .33, TI .69 vs .64, WM .00 vs .00).
- "Full-message accuracy is unacceptable for all models and settings, except for AS with EN
  compression" — AS with DA is now at the same level (.64 vs .65 strict, .75 vs .78 loose).
- "the advantage of using the EN architecture does not extend to DA" — AudioSeal performs
  as well under DA as under EnCodec.
- "retraining does not bring robustness to neural codecs up to acceptable levels" — it does
  for AudioSeal under DAC.
- "none of the considered watermarking algorithms survives the DA attack" — AudioSeal performs as well under DA as under EnCodec
  (bitwise .96, full-message .64 vs .65).
- Timbre's DAC robustness is understated by roughly 0.09 bitwise.

The broader finding is unchanged for the other models:
- Neural compression is the hardest attack class for SilentCipher, Timbre, and WavMark
- SilentCipher, Timbre, and WavMark are not robust under neural compression

## 2. The paper's MP3 numbers are not reproducible with this code

**In short.** In the code we used for the paper, the MP3 attack compressed the audio twice.
A first step encoded the signal to MP3 at the encoder's default bitrate, ignoring the bitrate the
benchmark had asked for; only the second step used the requested 64, 128 or 256 kbps. Since
the first step had already thrown information away, the requested bitrate made almost no
difference. All three settings ended up as almost the same attack, and a harsher one than a single
MP3 encode at any of those bitrates. The first encoding was a legacy encoding based on
torchaudio. It should have been removed when the ffmpeg-based implementation was introduced,
but was left in place. It was later removed during refactoring, without us realizing that it
had affected the results. The released code therefore compresses once, at the requested
bitrate.

**In the code.** The MP3 attack is `get_mp3()`, which writes the audio to a temporary file
and calls ffmpeg with `-b:a <bitrate>`. In the code we used for the paper, one more encode
ran before that, through a helper named `compress()`:

```python
wav_tensor_flat, _ = compress(wav_tensor_flat, sr, bitrate=bitrate)   # removed since
```

That helper handed the bitrate to `torchaudio.save(..., format="mp3", bits_per_sample=...)`.
`bits_per_sample` is a bit depth (16, 24, 32), not a bitrate, so a value like `128` never
reached the encoder as a bitrate and torchaudio's own default was used instead. With torchaudio
2.1.0 (ffmpeg backend), the first step was therefore always encoded at the encoder's default
bitrate: 24 kbps for the 16 kHz models and 32 kbps for the 22.05 kHz model. That is why
the first step came out the same no matter what the config asked for, and why it set the
ceiling on everything that followed.

Measured on a 3 s excerpt at 16 kHz:

| Requested bitrate | Released code | Paper's code |
|---|---|---|
| 64k | 25.72 dB SNR | 17.38 dB SNR |
| 128k | 26.01 dB SNR | 17.38 dB SNR |
| 256k | 26.01 dB SNR | 17.38 dB SNR |

All three bitrates therefore produce almost the same attack. Table 2 lists the MP3 bitrate range
as {64, 128, 256} kbps; in practice the loose setting (128k/256k) measured the same
default-bitrate encode as the strict setting rather than those bitrates.

`compress()` was called only from `get_mp3()`, so AAC and Vorbis are unaffected; their
numbers reproduce within run-to-run variation.

**Status.** The released code performs a single ffmpeg encode at the requested bitrate,
which is the intended behavior, so no code change is needed. If you compare against the MP
column of Table 5, expect it to differ; the values this code produces are listed below (see the appendix linked
above for details).

**What this code produces (MP column).**

| Model | Eval | Bitwise (paper -> this code) | Full-message (paper -> this code) |
|---|---|---|---|
| AS | S | ✓ -> ✓ | .92 -> .94 |
| AS | L | ✓ -> ✓ | .93 -> .95 |
| SC | S | .54 -> .57 | .14 -> .18 |
| SC | L | .57 -> **.87** | .17 -> **.70** |
| TI | S | ✓ -> ✓ | .92 -> .93 |
| TI | L | ✓ -> ✓ | .94 -> .98 |
| WM | S | .42 -> .48 | .29 -> .34 |
| WM | L | .48 -> **✓** | .34 -> **.98** |
| AS* | S | ✓ -> ✓ | ✓ -> ✓ |
| AS* | L | ✓ -> ✓ | ✓ -> ✓ |
| SC* | S | .98 -> ✓ | .85 -> .91 |
| SC* | L | .98 -> **✓** | .87 -> **.98** |

Note that the strict rows change too, not only the loose ones. The paper's strict setting
was the default-bitrate encode followed by a 64 kbps encode, not a 64 kbps encode on its own,
so its MP values are not a measurement of 64 kbps either.

A related point is visible in the table: in the paper the two settings give almost the same
MP numbers, which is what you would expect if the requested bitrate never took effect.

| | paper S | paper L | this code S | this code L |
|---|---|---|---|---|
| WM, bitwise | .42 | .48 | .48 | **✓** |
| SC, bitwise | .54 | .57 | .57 | **.87** |

With the bitrate applied the two settings separate widely; without it they do not. The
strict/loose distinction for MP therefore carries little information in the published
table.

**Effect on the paper's conclusions.** The ranking under MP3 is unchanged at 64 kbps:
WavMark and SilentCipher are still the models most damaged by it. At 128/256 kbps the
damage disappears for WavMark and becomes much smaller for SilentCipher (bitwise .87,
full-message .70), so the following statements need revising:

- "WM is notably affected by MP compression" holds at 64 kbps but not at 128/256 kbps.
- The same applies to SilentCipher's vulnerability to MP3.
- "even after retraining, models continue to struggle with compression (EN, DA, MP, OG)" —
  after retraining, SilentCipher reaches ✓/.91 under MP3 (strict), and AudioSeal .98/.86
  under DAC.

## Reproducing these numbers

The corrected values were produced with this repository at the commit that introduces the
DAC fix, using the released configs and the paper's evaluation seeds. Because each row of
`data/test_{strict,loose}.csv` already fixes the attack and its parameters, a single attack
can be re-evaluated by filtering the test set:

```bash
awk -F'|' 'NR==1 || $10=="dac"' data/test_strict.csv > test_strict_dac.csv

python scripts/eval.py \
    run_dir=runs/audioseal/dac_strict_seed42 \
    ffmpeg4codecs=ffmpeg/ffmpeg-7.0.2-amd64-static/ffmpeg \
    dataset.test_path=test_strict_dac.csv \
    random_seed_for_eval=42 \
    --config-name=../configs/audioseal/eval_strict.yaml
```

Seeds used per model follow the paper: AudioSeal and WavMark 42/2025/2026, Timbre
42/2024/2025, SilentCipher 42/2025/2026.
